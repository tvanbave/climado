### B. Seasonal Transitions

### E. Automatic Fuel Selection (Gated)

Only implement live control after the equipment and control gates below pass.
Until then, cost comparisons are advisory, not commands.

- Compare delivered heat cost using electricity price by ULO tier, heat-pump
  COP at outdoor temperature, marginal gas cost and furnace efficiency.
- Exclude fixed monthly charges from the marginal switching calculation;
  include applicable usage-based charges with consistent units.
- Treat economic crossover, capacity limit and manufacturer operating limits
  as distinct inputs. Do not invent a universal outdoor cutoff.
- Require an explicit user opt-in, a supported fuel control path, hysteresis,
  minimum dwell time and confirmed transitions to avoid repeated switching.
- Keep equipment interlocks/protection under the approved equipment controls;
  do not command simultaneous operation or bypass manufacturer limits.
- Define failure handling for stale/missing outdoor temperature, missing prices,
  invalid performance data, failed selection and HA restart. Use a verified,
  equipment-approved fallback, not an assumed automatic Ecobee handoff.
- Warn on inability to reach target or confirm fuel selection. Do not claim HA
  automation provides independent freeze protection or backup heating.

### F. Outdoor-Temperature-Based Cost Comparison

This is a required part of the fuel recommendation, not a future enhancement.
Use the current outdoor temperature to estimate heat-pump efficiency and compare
the cost of an equal amount of delivered heat from each source.

Inputs and calculation:

- Read a configured outdoor temperature sensor, with explicit units, validity
  and freshness checks. Recalculate on meaningful temperature changes, exact
  electricity-tier boundaries, and changes to prices or performance settings.
- Obtain a COP-versus-outdoor-temperature table for the confirmed heat pump and
  matched indoor equipment. Record its source, test conditions and applicable
  operating range. Do not substitute a seasonal efficiency rating for COP at
  the current temperature.
- Interpolate only within the validated performance table. Account for load,
  staging and defrost where supported by the supplied data; otherwise label
  the result as an estimate and use an uncertainty margin. Do not invent a
  correction factor or extrapolate below the available temperature range.
- Compare costs in the same currency per kWh of delivered heat:
  `heat_pump_cost = electricity_cost_per_kWh / estimated_COP(outdoor_temp)`.
- For gas billed by volume:
  `furnace_cost = gas_cost_per_m3 / (gas_energy_kWh_per_m3 * furnace_efficiency)`.
  Use the applicable billing energy conversion, an efficiency fraction and
  consistent energy/efficiency definitions. Treat rated furnace efficiency as
  an estimate, not a measured instantaneous value. Include material ancillary
  electricity use where known without double-counting it in heat-pump COP.
- Show outdoor temperature, estimated COP, both delivered-heat costs, preferred
  source and the reason. Keep the cost recommendation separate from the source
  actually running and from the source currently allowed by equipment limits.
- A source must meet operating limits and required heating capacity before it
  is eligible for automatic selection. Comfort and equipment protection take
  precedence over a nominally cheaper estimate.
- Near equal costs, retain the current eligible source using a configured
  savings/uncertainty margin and minimum dwell time. Missing or invalid inputs
  produce an unavailable comparison, never a fabricated cheapest-source result.

The economic crossover is therefore dynamic: the same outdoor temperature can
produce a different recommendation in ultra-low and on-peak periods. No fixed
outdoor switchover temperature is a substitute for this calculation.

## Implementation Order and Code Map

1. Capability audit and profile design: record read-only HA findings and resolve
   the gates. No guessed service names or equipment thresholds.
2. Profile configuration: `const.py`, `config_flow.py`, `number.py`, translation
   resources. Preserve existing cooling identifiers and restored values; add
   explicit opt-in heating configuration and migration tests.
3. Heating policy: `coordinator.py` evaluation, target/preset application,
   command matching, mode-change handling and runtime persistence. Extend the
   existing serialised command path instead of adding competing writers.
4. Rate and pre-arrival policy: `rate.py`, `coordinator.py`, `__init__.py`,
   `services.yaml` and `button.py`. Preserve current schedule and service users.
5. Status/card: `sensor.py` and `frontend/climado-card.js`. Separate comfort
   state from HVAC mode and observed equipment; retain pending/error feedback.
6. Advisory cost model, followed by optional fuel commands only when gates
   pass. Keep policy calculations separately testable from device I/O.
7. Regression tests, supervised validation and release notes. Bump versions
   and publish to HACS only after the implemented scope passes release gates.
